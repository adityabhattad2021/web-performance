Web Performance

You have a React app. We'll measure its performance, understand what's slow, fix it, and verify improvement — step by step.

The loop: Measure → Diagnose → Fix → Verify. Never guess. Always profile first.

// phase 1 — measure

Opening DevTools &
Setting Up

Before recording, set up Chrome for accurate results. Your dev machine is fast — we need to simulate a real user's device.

1

Open DevTools

Right-click anywhere on your page → Inspect, or use keyboard:

F12 or Cmd+Option+I (Mac) or Ctrl+Shift+I (Windows)
2

Navigate to the Performance tab

Click "Performance" in the DevTools tab bar. If you don't see it, click the >> overflow menu.

3

Enable CPU throttling — CRITICAL step

At the top of the Performance panel, find the CPU dropdown. Set it to 4x slowdown (or 6x for mobile simulation). Your dev machine has a fast CPU — users don't. This makes slow code visible.

Where to find it
Performance tab → top toolbar → CPU: No throttling → change to 4x slowdown
4

Enable Network throttling (optional but recommended)

In the Network panel, find the throttling dropdown (says "No throttling"). Set to Fast 3G or Slow 3G to simulate real network conditions. This reveals load-order issues.

5

Use Incognito / Private Window

Extensions distort profiles. Open your app in a Private/Incognito window with no extensions, then open DevTools there. This gives clean, uncontaminated results.

Cmd+Shift+N (Mac) or Ctrl+Shift+N (Windows)
// phase 1 — record

Recording a
Performance Profile

There are two recording modes. Choose the right one for what you're measuring.

⏺ Record button

Click the circle button, interact with your app (scroll, click, navigate), then stop. Best for: interactions, animations, clicking a button that feels slow.

🔄 Reload button

Click the reload icon — it records page load from scratch. Best for: measuring initial load time, Time to Interactive, paint metrics.

1

For initial load performance

Click the ⟳ reload icon (not the circle). DevTools will reload the page and record everything from the first byte until the page becomes interactive. Stop after 5–10 seconds.

2

For interaction performance

Click the ⏺ record button. Then perform the interaction you want to profile (e.g., type in a search box, click a button, scroll a list). Click Stop after 2–5 seconds.

3

Keep recordings short

3–10 seconds is ideal. Longer recordings become huge files that are slow to analyze. One action at a time = easier to pinpoint what's slow.

Core Web Vitals
& What They Mean

These are the metrics Google uses to measure real user experience. Know what you're looking at before reading a profile.

LCP
Largest Contentful Paint
✓ < 2.5s ~ 2.5–4s ✗ > 4s
When does the biggest visible element (hero image, heading) finish rendering? This is the user's perception of "it loaded."
INP
Interaction to Next Paint
✓ < 200ms ~ 200–500ms ✗ > 500ms
How fast does the page visually respond when the user clicks/taps? Slow = the JS main thread is blocked.
CLS
Cumulative Layout Shift
✓ < 0.1 ~ 0.1–0.25 ✗ > 0.25
Do elements jump around as the page loads? Images without dimensions, ads injecting late — all cause layout shift.
FCP
First Contentful Paint
✓ < 1.8s ~ 1.8–3s ✗ > 3s
When does the browser first paint anything (text, image, SVG)? A fast FCP reduces the "blank white page" perception.
TBT
Total Blocking Time
✓ < 200ms ~ 200–600ms ✗ > 600ms
Total time JS tasks blocked the main thread for 50ms+. High TBT = your page feels frozen. Heavily correlated with INP.
TTI
Time to Interactive
✓ < 3.8s ~ 3.8–7.3s ✗ > 7.3s
When is the page fully interactive and consistently responding to inputs? Before this, clicks might be ignored or delayed.
Where to see these in DevTools: In the Performance tab timeline, look for the colored vertical lines labeled FCP, LCP etc. In Lighthouse (separate tab), you get all scores at once.

Reading the
Flame Chart

The flame chart is the most powerful (and most confusing) part of the Performance panel. Here's how to decode it.

1

X-axis = time, Y-axis = call stack

Wide bars = long execution time. Tall stacks = deep function nesting. You want short, flat bars. A bar that spans the whole width is a problem.

2

Look for red "Long Tasks" triangles

Any task over 50ms blocks the main thread. Chrome marks these with a red corner. These are your primary enemies — the user's clicks are queued behind them.

3

Click on a bar to inspect it

Click any bar in the flame chart. The Summary panel below shows: Self time (time in this function) vs Total time (including children). High self time = the function itself is slow. Low self time but high total = the children are slow.

4

Find the widest bar at the bottom

The bottom of the stack = the leaf functions = where time is actually being spent. Find the widest bar near the bottom — that's your target.

5

Use the "Bottom-Up" tab

Below the flame chart, click "Bottom-Up". This sorts functions by total time, revealing the biggest time sinks regardless of call depth. This is often faster than reading the flame chart directly.

Color in DevTools What it means Significance
🟡 Yellow JavaScript execution Your app code, library code
🟣 Purple Rendering / Layout Style recalculation, reflow
🟢 Green Painting Pixels drawn to screen
🔵 Blue Parsing HTML/CSS Initial page load parsing
🔴 Red corner Long Task marker Immediate problem — investigate

Sort by Size — find bloated files

Click the Size column header to sort. Anything over 500KB deserves scrutiny. A vendor.js of 2MB+ is a red flag — it's all downloaded before your app can run.

2

Look at the waterfall column

Each bar shows TTFB (waiting, in lighter color) vs Download (darker). Long light bars = slow server. Long dark bars = large file. Bars that start late = render-blocking predecessors.

4

Filter by type

Click JS in the filter bar to see only JavaScript. Compare that to Img — often images are the biggest culprits. Check Font too — web fonts can block rendering.

// phase 2 — diagnose

Spotting Common
Bottlenecks

Now that you can read the tools, here's what to actually look for — the patterns that appear in almost every slow React app.

⚠️ Symptom: Long Task on every keystroke

What you'll see: In the flame chart, a wide yellow JS bar appears every time you type. Cause: A filter/search function is re-running on every render without memoization.

⚠️ Symptom: Massive initial JS payload

What you'll see: In Network, a huge vendor.js or main.js. In Performance, a long yellow parse+compile block before FCP. Cause: No code splitting — entire app is shipped as one bundle.

⚠️ Symptom: Layout thrashing (purple spikes)

What you'll see: Alternating yellow (JS) and purple (layout) bars in rapid succession. Cause: Code reads layout properties (offsetHeight, getBoundingClientRect) then writes CSS in a loop, forcing the browser to recalculate layout repeatedly.

⚠️ Symptom: Component re-rendering excessively

What you'll see: In React DevTools Profiler, a component lights up on every parent render even when its props didn't change. Cause: Missing React.memo, new object/array references on every render.

⚠️ Symptom: High CLS score

What you'll see: In Performance timeline, the CLS marker shows shifts. Elements jump as images/ads load. Cause: Images without explicit width/height, dynamically injected content above existing content.

// phase 2 — react

React DevTools
Profiler

Install the React DevTools extension. It adds a Profiler tab that shows exactly which components re-rendered and why.

1

Install React DevTools

Install from Chrome Web Store → "React Developer Tools". Once installed, DevTools gains a ⚛ Components and ⚛ Profiler tab.

2

Enable "Highlight updates when components render"

In the ⚛ Components tab → click the gear icon → check "Highlight updates when components render". Now, every time a component re-renders, it flashes. Interact with your app and watch what flashes.

If your whole page flashes green on every click, you have a re-rendering problem.
3

Record a Profiler session

Go to the ⚛ Profiler tab. Click the record button, perform an interaction (click a button, type in a field), stop. You'll see a flame chart of React component renders with exact timing.

4

Look at the "Ranked" chart

Switch to the Ranked chart view — it sorts components by render time, longest first. The components at the top are your bottlenecks.

5

Check "Why did this render?"

In Profiler settings, enable "Record why each component rendered". Click a component bar → the detail panel shows: "Props changed: items", "State changed: count", or "Parent re-rendered". This tells you exactly what to fix.

// phase 3 — fix

Performance
Improvements

Targeted fixes for the most common React performance issues. Each is expandable with code examples.

High Impact Code Splitting with React.lazy() ▶

The default Create React App / Vite setup ships all your code in one bundle. Code splitting breaks it into chunks that load on demand. Impact: Can reduce initial JS by 50–80%.

⚠ Before — one huge bundle
import Dashboard from './Dashboard';
import Settings from './Settings';
import Analytics from './Analytics';
// All loaded upfront, even if user
// never visits Settings or Analytics
✓ After — split by route
const Dashboard = lazy(() => import('./Dashboard'));
const Settings = lazy(() => import('./Settings'));
const Analytics = lazy(() => import('./Analytics'));
// Each route loads only when visited
import { lazy, Suspense } from 'react'; // Wrap lazy imports with Suspense function App() { return ( <Suspense fallback={<div>Loading...</div>}> <Routes> <Route path="/" element={<Dashboard />} /> <Route path="/settings" element={<Settings />} /> </Routes> </Suspense> ); }
High Impact React.memo + useMemo + useCallback ▶

By default, React re-renders a component every time its parent renders — even if the component's props didn't change. Memoization prevents unnecessary re-renders.

// React.memo — skip re-render if props unchanged const ProductCard = React.memo(({ product }) => { return <div>{product.name}</div>; }); // useMemo — cache expensive computation const filteredProducts = useMemo(() => { return products.filter(p => p.price > minPrice); }, [products, minPrice]); // only recompute when these change // useCallback — stable function reference for child props const handleDelete = useCallback((id) => { setItems(prev => prev.filter(i => i.id !== id)); }, []); // stable reference — won't trigger child re-render
Don't memoize everything — it has overhead too. Use it when: a component renders often AND is expensive to render, OR when you pass functions as props to memoized children.
High Impact Virtualize Long Lists ▶

Rendering 500 DOM nodes when only 20 are visible is a massive waste. Virtualization renders only the visible rows — the rest are virtual. Use @tanstack/react-virtual or react-window.

import { useVirtualizer } from '@tanstack/react-virtual'; function ProductList({ items }) { const parentRef = useRef(null); const virtualizer = useVirtualizer({ count: items.length, getScrollElement: () => parentRef.current, estimateSize: () => 60, // row height in px }); return ( <div ref={parentRef} style={{ height: '600px', overflow: 'auto' }}> <div style={{ height: virtualizer.getTotalSize() }}> {virtualizer.getVirtualItems().map(row => ( <div key={row.key} style={{ transform: `translateY(${row.start}px)` }}> <ProductCard item={items[row.index]} /> </div> ))} </div> </div> ); }
Med Impact Image Optimization ▶

Images are often the biggest payload. Use modern formats, right sizes, and lazy loading.

// Before: a 2MB JPEG served to everyone <img src="/hero.jpg" /> // After: WebP + fallback + lazy + correct dimensions <picture> <source srcSet="/hero.webp" type="image/webp" /> <img src="/hero.jpg" width="1200" height="600" loading="lazy" // browser-native lazy load decoding="async" alt="Hero image" /> </picture> // For above-fold images: use loading="eager" + fetchpriority="high" <img src="/hero.jpg" fetchpriority="high" />

Also: run images through Squoosh or Sharp to compress. WebP is typically 25–35% smaller than JPEG at the same quality.

Med Impact Debounce Expensive Operations ▶

Search/filter inputs that run on every keystroke cause constant re-renders. Debounce delays execution until the user stops typing.

import { useDeferredValue, useState } from 'react'; // Option 1: React's built-in useDeferredValue function SearchPage() { const [query, setQuery] = useState(''); const deferredQuery = useDeferredValue(query); // deferredQuery lags behind — search runs with lower priority return ( <> <input onChange={e => setQuery(e.target.value)} /> <SearchResults query={deferredQuery} /> </> ); } // Option 2: Manual debounce with useCallback const debouncedSearch = useCallback( debounce((q) => fetchResults(q), 300), [] );
Med Impact Fix CLS — Add Dimensions to Images ▶

When images load without explicit dimensions, the browser doesn't reserve space — other content jumps when the image appears. This tanks your CLS score.

⚠ Causes layout shift
<img src="product.jpg" />
✓ Space reserved, no shift
<img
  src="product.jpg"
  width="400"
  height="300"
/>

Also fix: dynamically injected content (ads, banners) appearing above existing content. Use CSS min-height placeholders for async content.

Low Impact Preload Critical Resources ▶

Tell the browser to fetch critical assets early — before it discovers them in CSS or JS.

<!-- In your <head> --> <!-- Preload the LCP image --> <link rel="preload" as="image" href="/hero.webp" /> <!-- Preload your primary font --> <link rel="preload" as="font" href="/fonts/Inter.woff2" type="font/woff2" crossorigin /> <!-- Preconnect to API domain --> <link rel="preconnect" href="https://api.yourapp.com" />

Analyzing &
Shrinking Your Bundle

Use Bundle Analyzer to visualize exactly what's in your JavaScript — often you'll find surprises.

1

Install Bundle Analyzer (Vite)

npm install --save-dev rollup-plugin-visualizer

Add to vite.config.js:

import { visualizer } from 'rollup-plugin-visualizer'; export default { plugins: [ react(), visualizer({ open: true, gzipSize: true }) ] }

Run npm run build — a visual treemap opens in the browser.

2

Common bundle bloat culprits

In the treemap, look for unexpectedly large rectangles:

What you seeThe fix
moment.js (500KB+)Replace with date-fns or dayjs (<5KB)
lodash (500KB)Import specific functions: import debounce from 'lodash/debounce'
All of react-iconsImport only what you use: import { FiMenu } from 'react-icons/fi'
Unused routes/pagesApply React.lazy() code splitting
3

Enable compression on your server

Gzip or Brotli compression can reduce JS by 60–80% over the wire. This is a server config, not a code change — but one of the highest-ROI improvements available. Check if your server/CDN has it enabled.

// phase 4 — verify

Measure Again &
Compare

After applying fixes, re-profile with the exact same steps. Never trust feelings — trust numbers.

1

Re-run the same Performance recording

Use the same throttling settings, same page state, same interaction. Compare: are the Long Task bars shorter? Are there fewer re-renders in the flame chart?

2

Run Lighthouse before + after

DevTools → Lighthouse tab → Generate report. Do this before your changes and after. The Performance score and individual metric values give you a clear before/after comparison.

Run Lighthouse in incognito, with extensions disabled, at least 3 times and average the scores — results vary between runs.
3

Check Network panel totals

After code splitting + image optimization, the JS transferred and total resources should be meaningfully smaller. You might go from 3MB to 800KB — that's visible in the summary bar.

4

Use web.dev/measure for real-world data

If your app is deployed, run it through PageSpeed Insights (pagespeed.web.dev). This shows both lab data and real-world field data from Chrome users. Field data is the ultimate truth.

Performance
Checklist

Work through this list — click to check off items as you complete them.

  • Record a baseline Performance profile (with CPU 4x throttle)
  • Check Network tab — identify files over 500KB
  • Install React DevTools — enable render highlighting
  • Run Profiler — find components with excessive re-renders
  • Add React.lazy() to route-level components
  • Wrap expensive child components with React.memo()
  • Add useMemo to expensive filter/sort computations
  • Add useCallback to functions passed as props to memoized children
  • Virtualize any list with 100+ items (react-virtual / react-window)
  • Compress + convert images to WebP, add width/height attributes
  • Add loading="lazy" to below-fold images
  • Run Bundle Analyzer — replace moment.js / full lodash
  • Confirm Gzip/Brotli compression is enabled on server
  • Re-record Performance profile — compare Long Tasks
  • Run Lighthouse before + after — confirm score improvement
